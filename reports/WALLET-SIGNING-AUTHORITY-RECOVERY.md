# Wallet & signing-authority recovery — final determination

**Date:** 2026-11-14 · **Network:** NEAR testnet · **Scope:** recover the original signing capability
OpenHands created/managed for the two live Overcover contracts, without replacing identities or losing
state. **No secret material was printed, copied, or transmitted during this investigation.**

## Verdict

> **The original signing authority is NOT recoverable.** The keys were generated by
> `KeyPair.fromRandom("ed25519")` inside **earlier OpenHands sandboxes** and written only to that
> sandbox's git-ignored `keys/` directory. Sandboxes are ephemeral and single-use; the generating
> sandbox's filesystem is gone, the keys were never committed, exported, or bound to any registered
> secret, and NEAR has no key escrow or owner-recovery path. There is **no authorized procedure** to
> sign as either contract account, and **no key-rotation path that does not already require the
> missing key**.
>
> This is a **hard, evidence-based blocker**, not an environment omission. The product remains
> functional on the live v3 contract; only the two owner-only remediations (in-place v3 redeploy,
> legacy v1 pause) are unreachable.

## 2. Where the keys went — and why they are gone

| Question | Finding |
| --- | --- |
| Which session generated the key? | The legacy keys: the 2026-11-10 session (`133d392`). The v3 keys: the 2026-11-12 **run-3** session (evidence at `a189ad6`, 13:46 UTC). |
| Which mechanism? | `near-api-js` `KeyPair.fromRandom("ed25519")`, in-process, written to a git-ignored file. No HSM, no platform key service. |
| Persisted or ephemeral? | **Persisted only on the generating sandbox's local disk** — which is ephemeral. Never committed, exported, or bound to a durable store. |
| Which storage/binding is missing? | The generating sandbox's `/workspace/project/overcover/keys/` (the `identities.json` for v1; `controlled-v3.json` + `controlled-v3-root.json` for v3 run 3). |

### Why the generating sandbox's keys cannot be reached

- **This sandbox is a different, later sandbox.** Conversation `9383c8e7a5ff4066b7f0688455c35dc0` was
  created **2026-11-12 22:31 UTC** (earliest bash event 22:45 UTC) — **~9 hours after** the run-3 v3
  deploy (13:46 UTC). Sandboxes do not share filesystems: only this sandbox's `/workspace` and
  `/var/openhands` are mounted.
- **The keys file was overwritten in place.** `KEYS_OUT` is a single fixed path
  (`keys/controlled-v3.json`). Run 4 (`contract.ovc-v3-ctl-mwgci3u8.testnet`) was the last writer; the
  file now holds **only** the run-4 graph and **zero** `2f6c4c` entries. `keys/controlled-v3-root.json`
  is absent. So even the run-3 keys that once landed on a shared path were clobbered.
- **Never committed.** `git log --all --diff-filter=A -- 'keys/*'` shows `keys/` was never added;
  a scan of every git object (`git rev-list --objects --all` → `git cat-file`) found **0** secret-shaped
  `ed25519:` strings; `.gitignore` line 2 is `keys/`.
- **No registered secret is a NEAR key.** All 15 environment secrets are JWTs or API tokens
  (GitHub/GitLab/Vercel/Groq/Gemini/Supabase/OutLayer/…); **none** matches `ed25519:`. No secret
  provides a NEAR signer.
- **No other store holds one.** `~/.near-credentials/`, `~/.near/` absent; `~/.openhands/{profiles,
  provider-connections}` empty; `~/.openhands/cache` and `git-credentials` hold only git tokens; no
  NEAR key in any OpenHands conversation artifact or bash event.

## 3. Authorized recovery / rotation — none exists

- **NEAR has no key escrow or owner-recovery.** The only way to sign as `contract.ovc-v3-ctl-2f6c4c.testnet`
  or `contract.attestor-overcover.testnet` is the private half of their single FullAccess key.
- **Adding a key cannot bootstrap from nothing.** `AddKey`/`DeleteKey`/`DeployContract` are signed *as
  the account* — they require the missing key.
- **The contract's own rotation methods do not help.** v3 exposes `rotate_operator_key`, `add_operator`,
  `add_resolver`, `set_attestor`, `set_paused`, `add_product`, … but every one is **owner-only**
  (`assert_owner`, `contract/src/lib.rs:762`). They require the owner's key first, so they cannot
  recover access.
- **A fresh deployment is not a substitute.** It would create a *new* account and cannot remediate the
  existing address or preserve its identity/state — and the mission explicitly rules this out.

**Conclusion:** no authorized account-recovery or key-rotation procedure exists. The keys are
unrecoverable and cannot be replaced.

## 4. Controlled operations — prepared, not executed (authority not recovered)

These are the exact operations that *would* run if the keys existed. They are prepared and verified
against source; **none was executed**, because the authority is absent.

**A. In-place hardened v3 upgrade (code-only, state-preserving):**

```bash
node driver/redeploy-v3.mjs --plan            # prints one DeployContract; sends nothing
OVC_EXPECTED_SHA=811e0427ec467582913a47400ecf1b7c272ddea20ff5074f04a4513d896c0a7f \
  OVC_V3_SECRET_KEY=<FullAccess key of contract.ovc-v3-ctl-2f6c4c.testnet> \
  node driver/redeploy-v3.mjs                 # DeployContract only; no new()/migrate()
```
Fails closed unless the wasm is exactly `811e0427…` and carries the SEC-9 guard. Reversible
(redeploy `a97034e6…`). The console already trusts both hashes, so buying is uninterrupted.

**B. Pause legacy v1 (one call, preserves all 15 policies):**

```bash
near call contract.attestor-overcover.testnet set_paused '{"paused": true}' \
  --accountId owner.attestor-overcover.testnet
```

**C. Independent verification (ready, keyless):** `npm run verify:preservation --
--expect-sha256 811e0427…` (diffs every state view + all policies vs
`proof/preservation-snapshot.json` and re-asserts `reserved ≤ capital`); `npm run verify:release-ops`
(reads pause state, code hashes, operator-credential absence).

**D. Owner-led human acceptance:** `docs/HUMAN_ACCEPTANCE_TEST.md` — runs on the live v3 contract as-is
and does not depend on A or B.

## 5. Exact remaining owner action

Because the keys are gone and cannot be regenerated:

- **In-place hardened upgrade of `contract.ovc-v3-ctl-2f6c4c.testnet` is not possible.** If a hardened
  deployment on the *production* address is required, it must be done by whoever can obtain a
  FullAccess key for that account (i.e. it cannot be done by anyone, given the key is destroyed).
- **Legacy v1 cannot be paused or repaired.** It remains disclosed, labelled, and non-purchasable in
  the console, and `migrate()` stays callable by any account (SEC-1, live).
- **The one action a human can still complete today** is the **live v3 human wallet purchase** —
  a buyer's own wallet, not the owner's key. That is the acceptance test in
  `docs/HUMAN_ACCEPTANCE_TEST.md`, and it needs no Overcover key.
